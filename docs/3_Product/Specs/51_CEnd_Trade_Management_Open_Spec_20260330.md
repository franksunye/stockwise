# 功能规格说明书：C 端交易管理开放（Spec 51）

## 1. 一句话定义

**C 端交易管理开放，不是把研究系统搬到前台，而是把已存在的持仓管理能力压缩成用户可执行的“状态 / 动作 / 纪律”输出。**

---

## 2. 正式定位

### 2.1 这条能力是什么

交易管理前台能力的正式定位是：

**已持仓场景下的纪律执行层。**

它服务的是：

- 风险控制
- 利润保护
- 执行纪律

### 2.2 这条能力不是什么

它不是：

- 信号层替代品
- 券商终端
- 资产聚合器
- 自动交易产品
- 新的首页主入口

### 2.3 与现有产品层的边界

- `Investment Mode`：风险偏好层
- `Tactical / Council`：分析层
- `Trade Management`：执行层

一句话：

**择时回答“这只票怎么看”，管理回答“这笔仓怎么处理”。**

---

## 3. 当前判断

### 3.1 为什么现在可以做

当前已经具备三层基础：

1. 后台已有真实对象闭环：
   - 持仓主记录
   - 成交事件
   - 最新建议
   - advice log
   - admin 管理页
2. Dashboard 已有适合承接的单票上下文：
   - 个股卡片
   - `TacticalBriefDrawer`
   - 用户态分流
3. 前端架构允许局部 sidecar 接入，不适合再次推翻主链路

### 3.2 正式架构判断

交易管理前台开放应视为：

**面向已登录用户的私有 sidecar 数据面**

而不是：

- 并入 `/api/stock/batch`
- 重写 Dashboard 首页
- 直接做复杂独立工作台

---

## 4. 核心产品原则

### 4.1 UX 总方向

总方向定义为：

**AI 交易日记与纪律防线**

### 4.2 四条必须坚持的原则

1. `深层融合`
   - 融入单票上下文
   - 融入现有 Dashboard 抽屉体系
2. `极简非强制`
   - 不做逐笔精确记账型重后台体验
3. `包容性迁移`
   - 允许历史持仓粗颗粒度迁移
4. `真实持仓优先`
   - 不能长期依赖本地 `holding / empty / none` 假装真实持仓

### 4.3 产品表达原则

前台默认只压缩成三类输出：

1. `状态`
2. `动作`
3. `纪律`

---

## 5. 入口判断

### 5.1 默认入口

默认入口必须在：

**Dashboard 单票上下文**

### 5.2 自选池的角色

第一阶段：

- 不把自选池作为主入口

第二阶段：

- 可扩展为总览与分发入口
- 可选形态包括：
  - `已持仓 / 有建议 / 待处理` 筛选
  - 行级 badge
  - 新页签，例如 `持仓 / 管理中 / Portfolio`

### 5.3 入口文案

不建议用：

- `AI 接管`

建议方向：

- `建立持仓管理`
- `开启纪律追踪`
- `查看持仓建议`

---

## 6. TacticalBriefDrawer 的正式判断

### 6.1 长期正确结构

长期看，`TacticalBriefDrawer` 应升级为：

**单票决策抽屉**

一级视角建议收口为：

1. `战术`
2. `管理`

其中：

- `投研决议` 下沉为 `战术` 的复核层

### 6.2 当前约束

当前不能打破已经稳定运行的“择时”功能与现有 Tactical 使用习惯。

因此：

- 长期不应停留在三套并列世界
- 但 Phase 0 允许采用过渡性的三 tab 结构

---

## 7. Phase 0 最小功能集合

### 7.1 Phase 0 目标

**在不破坏当前择时稳定性的前提下，以过渡性的三 tab 结构让管理能力先进入 C 端前台。**

### 7.2 Phase 0 挂载方式

Phase 0 推荐方式：

**在当前 TacticalBriefDrawer 中新增第三个 tab：`管理`。**

Phase 0 的 tab 结构建议为：

1. `内参`
2. `决议`
3. `管理`

采用这个过渡结构的原因：

1. 当前 `内参` 内容已较饱满，不适合再硬塞一组管理模块
2. `管理` 的阅读任务与 `内参 / 决议` 明显不同
3. 三 tab 过渡结构比“把管理挤进内参”更清晰
4. 同时又不要求当前立刻重构为长期的 `战术 / 管理` 双视角结构

### 7.3 Phase 0 tab 文案

为适配三 tab 并排布局，Phase 0 建议采用双字文案：

1. `内参`
2. `决议`
3. `管理`

### 7.4 最小功能集合

Phase 0 最小功能集合收口为 6 项：

1. `仓位摘要条`
   - 剩余仓位 / 原始仓位
   - 成本价
   - 最近一次操作
2. `今日管理建议卡`
   - 当前状态
   - 今日主动作
   - 一句话纪律线
   - next trade date
3. `持仓状态标签`
   - 如：等待确认 / 盈利保护 / 风险抬升
4. `建议更新时间`
   - 让建议有时效感和可信度
5. `轻量操作区`
   - `查看管理详情`
   - `已执行` 或 Phase 0 降级为 `稍后处理`
6. `无持仓态轻入口`
   - 一句短说明
   - 一个 CTA

### 7.5 `管理` tab 的显示规则

`管理` tab 在 Phase 0 不应是摆设。

建议规则：

1. 当前存在真实持仓时，显示 `管理`
2. 当前无真实持仓、但允许录入时，也显示 `管理`
3. 当前无权限或完全未开放给该用户时，不显示 `管理`

这样用户进入 `管理` 时，始终会看到：

1. 已持仓态的管理内容
2. 或无持仓态的轻入口与最小录入路径

而不是进入一个空页面

### 7.6 无持仓态轻入口的正式判断

**无持仓态轻入口不是可选项，而是 Phase 0 成立的必备条件。**

因为如果没有它：

1. 用户无法知道管理能力存在
2. 用户无法进入录入闭环
3. 这条能力会在前台变成半隐藏状态

建议文案方向：

- `录入持仓后查看管理建议`
- `建立持仓管理`
- `开启纪律追踪`

### 7.7 Phase 0 的视觉约束

`管理` tab 必须轻，不能长成第二个复杂分析页。

必须避免：

1. 大块 onboarding 面板
2. 强打断表单
3. 多套复杂预案并排
4. 单独再叠一个同级重 modal

一句话：

**Phase 0 的 `管理` tab 是轻量执行页，不是第二个 Tactical。**

---

## 8. 最小录入能力

### 8.1 正式判断

**最小持仓录入能力，是 Phase 0 前台管理闭环的必备前置。**

### 8.2 最小录入字段

最小录入字段建议为：

1. 建仓日
2. 建仓均价
3. 持仓数量

### 8.3 两类录入模式

前台支持两类录入：

1. `新开仓录入`
   - 用户刚完成建仓
2. `历史持仓迁移`
   - 用户已持有一段时间，只录入当前成本价与当前仓位

### 8.4 必须写死的边界

不做：

- 券商级自动同步
- 实盘订单同步
- 自动对账

---

## 9. 产品对象模型

前台消费压缩后的产品对象，不直接消费研究对象。

### 9.1 `TradePositionCard`

建议字段：

- `position_id`
- `symbol`
- `stock_name`
- `entry_date`
- `entry_price`
- `position_size`
- `remaining_size`
- `latest_event_date`
- `latest_event_type`
- `latest_event_price`
- `latest_event_quantity`

### 9.2 `TradeManagementAdviceCard`

建议字段：

- `advice_id`
- `position_id`
- `latest_trade_date`
- `next_trade_date`
- `state_id`
- `signal_state`
- `action_summary`
- `discipline_summary`
- `rationale_summary`
- `recommended_policy`
- `updated_at`

### 9.3 `TradeExecutionEvent`

建议字段：

- `event_id`
- `event_date`
- `event_type`
- `quantity`
- `price`
- `note`

---

## 10. 数据契约

### 10.1 正式判断

不建议把交易管理并入：

- `/api/stock/batch`

建议使用独立用户私有接口，例如：

- `/api/user/trade-management/positions`
- `/api/user/trade-management/positions/:positionId`
- `/api/user/trade-management/positions/:positionId/advice`
- `/api/user/trade-management/positions/:positionId/events`

### 10.2 刷新策略

第一阶段建议：

1. Dashboard 主链路照旧
2. 管理数据按需拉取
3. 局部短 TTL
4. 不要求进入 Dashboard 即预取所有管理对象

---

## 11. 分期路线

### 11.1 Phase 0

目标：

- 在 TacticalBriefDrawer 中低风险开放 `管理` tab

范围：

- `内参 / 决议 / 管理` 三 tab 过渡结构
- 仓位摘要条
- 今日管理建议卡
- 持仓状态标签
- 建议更新时间
- 轻量操作区
- 无持仓态轻入口
- 最小持仓录入

### 11.2 Phase 1

目标：

- 让 Pro 用户在单票上下文里稳定看到真实持仓建议

范围：

- 只读持仓摘要
- 最新建议
- 建议历史
- 执行事件历史

### 11.3 Phase 2

目标：

- 轻量持仓账本

范围：

- 新建持仓
- 历史持仓迁移
- 自动重算剩余仓位
- 补录买卖事件

### 11.4 Phase 3

目标：

- 进阶解释层

范围：

- 状态解释
- 更强依据摘要
- 有限 policy 解释

---

## 12. 核心风险

1. `假个性化`
   - 没有真实持仓对象，却给出看似个性化的管理建议
2. `主链路污染`
   - 把管理数据混进 Dashboard 主数据链
3. `过度暴露研究结构`
   - 一开始就展示 lane、评分板、参数细节

---

## 13. 验收标准

- [ ] 已明确交易管理是“持仓纪律执行层”，不是信号替代层
- [ ] 已明确前台以 sidecar 方式接入，不并入主 batch
- [ ] 已明确 Phase 0 采用 `内参 / 决议 / 管理` 三 tab 过渡结构
- [ ] 已明确 Phase 0 最小功能集合为 6 项
- [ ] 已明确“无持仓态轻入口 + 最小持仓录入”是 Phase 0 必备条件
- [ ] 已明确不做券商级自动同步
- [ ] 已明确自选池是二阶段总览与分发入口，而不是一期主入口

---

## 14. 当前定稿结论

1. 交易管理适合开放到 C 端
2. 但只能以单票上下文中的 sidecar 方式开放
3. Phase 0 先以 `内参 / 决议 / 管理` 三 tab 过渡结构进入前台
4. Phase 0 的最小闭环是：
   - 无持仓态轻入口
   - 最小持仓录入
   - 持仓管理卡展示
5. 长期再把 TacticalBriefDrawer 收口为 `战术 / 管理` 双视角结构

一句话收口：

**先把管理做成一张可信、可执行、可进入的轻量持仓卡，再逐步长成完整执行层。**
