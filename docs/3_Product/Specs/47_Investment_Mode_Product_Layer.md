# 功能规格说明书：投资模式（Investment Mode）(Spec 47)

## 1. 文档定位

本 Spec 只保留产品层后续真正会反复使用的内容：

1. Investment Mode 是什么
2. Investment Mode 不是什么
3. 它和交易管理引擎的边界
4. 当前产品层如何收口
5. 当前内部试用版已经长成什么样
6. 后续如何继续演进

不再保留：

- 过程性讨论
- 早期 UI 想法的完整铺陈
- 已经被母本吸收的研究解释

---

## 2. 产品总原则

### 2.1 总定位

StockWise 的产品原则保持不变：

- 底层专业
- 表层极简
- 面向 2C 决策，不是专业交易工作台

### 2.2 产品层收口原则

前台最终不展示研究评分板，而是尽量压缩成三类输出：

1. `状态`
2. `动作`
3. `纪律`

也就是说，产品价值不是“让用户理解更多指标”，而是“把复杂研究压缩成可执行纪律”。

### 2.3 内外复杂度原则

必须坚持：

1. 内部复杂，外部简单
2. 研究多尺子，前台单结论
3. 默认只展示用户能执行的结果

---

## 3. 中国市场颜色语义

在中国市场语境下，必须明确分开：

- **价格颜色**
- **决策颜色**

### 3.1 价格颜色

- 上涨 / 浮盈 / 红盘：红色
- 下跌 / 浮亏 / 绿盘：绿色

### 3.2 决策颜色

- `TriggeredLong / TrendHolding`：暖红系或正向强调色
- `Watch / BreakoutPending`：蓝色
- `ProfitProtection`：琥珀色
- `RiskOff / FailureRisk`：深橙、棕红或警示色

### 3.3 必须写死的原则

1. 价格颜色服务“市场事实”
2. 决策颜色服务“系统判断”
3. 不允许信号层、交易管理层、表现层各自发明不同颜色系统

---

## 4. Investment Mode 的正式定义

### 4.1 模式是什么

Investment Mode 是用户侧的**决策偏好层**。

它负责把同一套市场判断转译成不同风险风格，例如：

- 稳健
- 平衡
- 进取

### 4.2 模式不是什么

Investment Mode 不是：

- 模型本身
- 单一策略版本
- 单条信号
- 裸参数工作台
- 完整的交易管理引擎

### 4.3 模式与底层关系

当前仍保持：

`mode_id -> strategy_version + params_bundle + display_policy`

模式的本质是把“出手条件与风险立场”产品化，而不是把研究参数直接商品化。

---

## 5. Investment Mode 与交易管理的边界

### 5.1 当前 Mode 负责什么

当前 `Investment Mode` 负责：

- 把市场判断转译成不同风险风格
- 让用户选择“更稳 / 更平衡 / 更进取”的决策偏好

### 5.2 当前 Mode 不负责什么

当前 `Investment Mode` 不负责完整解决：

- 已有仓位何时部分止盈
- 何时移动纪律位
- 何时允许加仓
- 何时认定失败突破并退出

### 5.3 这些问题属于什么

这些问题属于未来的：

**Trade Management Engine**

它依赖：

- 信号状态
- 持仓状态
- 管理策略
- 历史研究与生产观察

### 5.4 一句话边界

**Investment Mode 是交易管理产品层的第一阶段入口，不是完整交易管理系统。**

---

## 6. 模式系统与持仓状态机的双层结构

当前产品层采用固定双层结构：

### 6.1 面向用户：模式系统

用户优先理解和选择的是：

- 稳健
- 平衡
- 进取

这是产品入口层，也是默认展示层。

### 6.2 面向系统：持仓状态机

系统内部实际按仓位生命周期运行，例如：

- 建仓期
- 确认期
- 趋势延续期
- 盈利保护期
- 风险抬升期
- 退出期

默认不要求普通用户直接理解完整状态机。

### 6.3 渐进披露原则

- 普通用户先看到模式与执行卡
- 进阶用户再逐步看到状态解释

一句话：

**模式决定“你希望怎样被管理”，状态机决定“系统判断当前这笔仓应如何被管理”。**

---

## 7. 当前后台闭环 POC

在正式前台产品化之前，交易管理已经允许以后台闭环形态存在。

当前后台闭环已经具备：

1. 持仓主记录
2. 成交事件时间线
3. 最新建议卡
4. webhook 推送
5. advice log
6. ADMIN 管理与详情页

这条链路的意义是：

- 先验证真实闭环
- 先让“状态 / 动作 / 纪律”进入真实交付
- 后续前台只是消费同一套建议对象，而不是重写逻辑

---

## 8. 当前建议卡的正式定位

### 8.1 当前卡片不是静态建议卡

当前内部试用版建议卡已经从：

- 单笔静态持仓建议

升级为：

**带最近执行上下文的剩余仓位决策卡**

### 8.2 当前建议卡表达什么

当前卡片已经能表达：

- 当前剩余仓位 / 原始仓位
- 最近操作
- 当前建议是针对剩余仓位，而不是回看式重算

### 8.3 当前卡片的三层结构

当前产品化卡片按三层理解：

1. `判断层`
   - 当前状态
   - 成功分支
   - 失败分支
2. `执行层`
   - 默认执行方式
   - 备选执行方式
3. `依据层`
   - 为什么默认推荐这个执行方式

### 8.4 当前 webhook 形态

在企业微信 webhook 中，当前最佳落地方式是：

- 主卡承载：判断层 + 主执行层
- 第二条文本承载：依据层

这样做的原因不是简化逻辑，而是适配 webhook 模板的版面约束。

## 9. 当前产品化阶段

截至当前阶段，交易管理产品层可以正式视为：

**Internal Beta v1**

它已经具备：

- 后台录入与管理
- 自动 advice loop
- webhook 决策卡
- 去重发送
- ADMIN 持仓管理
- 详情联动

但它还不是：

- C 端最终形态
- 完整绩效展示页
- 完整执行偏差分析产品

---

## 10. 下一阶段

后续最自然的产品衔接方向已经明确：

### 10.1 已实现盈亏层

后续需要补上：

- 已实现盈亏
- 未实现盈亏 + 已实现盈亏的合并视角

### 10.2 建议 vs 实际执行偏差层

后续需要能回答：

- 系统建议了什么
- 用户实际做了什么
- 偏差发生在哪里

### 10.3 更完整的用户执行模式

后续可以继续长出：

- 盘中判断
- 条件单保护
- 用户风格路由
- 用户交易习惯适配

---

## 11. 一句话总结

当前产品层已经收口为一个很清楚的结构：

- Investment Mode 负责用户风险风格入口
- Trade Management Engine 负责持仓生命周期判断
- 前台最终压缩成状态、动作、纪律
- 当前已形成后台闭环与内部试用版

后续不是继续往产品里堆建议句子，而是沿固定链路继续长：

**对象 -> 逻辑 -> 表现**
