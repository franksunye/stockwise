# LLM 输出稳定性作战手册（SEO/GEO）

更新时间：2026-03-05  
适用范围：`StockWise` 股票分析链路（本地验证 + 生产发布）

## 1. 目标与边界
- 第一目标：稳定性优先于“更聪明”或“更花哨”的输出。
- 第二目标：在不显著降低用户价值的前提下，控制输出长度与结构一致性。
- 变更边界：生产链路坚持“小步快跑”，避免一次性大改 prompt + parser + schema。

## 2. 核心原则
- 单点变更原则：每次只动一个高置信度点，便于归因与回滚。
- 证据驱动原则：以 `llm_traces` 与离线测试结果为准，不靠主观感觉。
- 失败可见原则：有返回但解析失败必须可告警、可追踪、可复盘。
- 通用能力优先：解析器做“通用漏斗”，不做模型特化补丁堆叠。

## 3. Prompt 策略（小幅修订）
- 保持 JSON 契约清晰：字段、类型、必填项明确且稳定。
- 文本风格约束：简明、要点化、避免过程叙述和重复解释。
- 避免激进参数叠加：不为了“强控格式”同时引入多项高漂移风险设置。
- 允许轻微超限：`summary` 偶发略长可接受，但结构必须稳定可解析。

## 4. Parser 策略（通用漏斗）
- 分层解析顺序：
  1. 严格 JSON 解析
  2. 规范化后再严格解析（引号/全角/尾逗号等）
  3. 容错解析回退（如 dirtyjson，可选）
- 标准化诊断输出：
  - `NO_JSON_BLOCK`
  - `INVALID_JSON`
  - `TRUNCATED`
  - `SCHEMA_VALIDATION`
- API 兼容：保留原有 `parse_ai_response(...)` 调用面，新增诊断版本以支持观测。

## 5. 失败处理策略（止损）
- 规则：`LLM 有返回 + 解析失败` 时，立即通知 `ADMIN`，并停止该次重试。
- 目的：避免重复请求带来的成本放大与噪声放大。
- 补充：接口层错误（401/402/超时/URL 配置）独立归类，不与解析错误混淆。

## 6. 发布策略（GitHub -> Vercel）
- 发布前最小检查：
  - 关键单测通过（parser funnel + parse_failed hotfix）
  - 本地链路可跑通（`DB_SOURCE=local`，禁止写云端）
  - 改动范围可解释、可回滚
- 发布后观察窗口：
  - 先看 24-48 小时稳定性，再决定是否继续下一步优化
- 回滚触发条件（任一满足）：
  - `parse_failed` 比例显著上升
  - 输出字段缺失率明显上升
  - 用户侧语义价值出现明显下降

## 7. 指标与观测（Week 3 延后执行）
- 当前决定：网站发布满 2 周后再启动统计填报。
- 重点指标：
  - `success / parse_failed / error` 比例
  - `response_raw` 长度分布（按模型、按股票）
  - 关键字段完整率（summary/reasoning/action/risks 等）
  - 告警数量与恢复时间

## 8. 版本沉淀建议
- `22_DeepSeek_Local_DB_Diagnosis.md`：保留为“事故证据文档”（历史事实，不频繁改）。
- 本文档（`23_*`）：作为“长期策略与操作标准”，持续小步更新。
- 每次策略变更建议在文末追加：
  - 变更日期
  - 变更点
  - 验证结论

## 9. 下一阶段建议（低风险优先）
1. 仅继续 prompt 小幅收敛，不改核心调用流程。
2. 观察 parser 诊断码分布，识别是否仍有高频退化模式。
3. 两周后启动指标统计，基于数据再评估是否需要下一轮优化。
