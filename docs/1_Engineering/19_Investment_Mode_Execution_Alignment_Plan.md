# 19 Investment Mode Execution Alignment Plan

更新时间：2026-03-09  
状态：Active  
定位：执行对齐文档（先统一文字口径，再推动实现收敛）

## 1. 目标

这份文档用于解决当前 Investment Mode / tradeability 双线体系中的一个现实问题：

**团队共识已经开始收敛，但文档口径、后台展示口径和代码现状还没有完全一致。**

因此，当前最重要的工作不是继续扩写概念，而是明确：

1. 什么是当前事实（As-Is）
2. 什么是目标态（To-Be）
3. 哪些先按事实写清楚
4. 哪些作为下一阶段实现目标推进
5. 文档、后台、脚本应按什么顺序收敛

---

## 2. 当前共识（本轮确认为准）

### 2.1 生产线 vs 实验线

1. 我们有两条线：
   - 生产线：面向正式用户结果
   - 实验线：面向研究池、算法实验、版本比较
2. 两条线必须明确分口径，不能混成一个结果池。
3. PC 端 Admin 要同时承接两条线，但展示必须明确区分。

### 2.2 投资模式口径

1. 生产侧当前对用户可见共有 4 个模式：
   - `稳健`
   - `平衡`
   - `进取`
   - `仅观察`
2. 其中 `稳健 / 平衡 / 进取` 是核心模式：
   - 需要持续量化优化
   - 需要比较和升级治理
3. `仅观察` 是特殊模式：
   - 属于正式生产模式
   - 但不参与“最优参数”竞争
   - 不以量化回测找最优为主要目标

### 2.3 后台查看口径

1. 当前 PC 后台看生产数据时，不以“模式总和”作为核心指标。
2. 当前重点是看每个模式各自的绩效。
3. 判断目标是：
   - 每个投资模式分别为用户提供了什么价值
   - 当前默认模式是否合理
   - 三个核心模式是否各自成立

### 2.4 实验到生产

1. 实验结果不能直接切生产。
2. 必须经过：
   - `verdict`
   - `approval`
   - `promote`
   - `rollback`
   - `audit`

---

## 3. 当前事实（As-Is）

以下内容是当前仓库实现层已经成立的事实，文档必须承认它，不应提前把目标态写成既成事实。

### 3.1 已经成立的事实

1. 模式体系已落地：
   - 后端已有 4 个 mode 定义
   - 前端/API 已支持模式目录、模式切换、模式绩效查询
2. 生产侧三层结果表已落地：
   - `mode_decision_log`
   - `mode_simulated_trade_ledger`
   - `mode_performance_snapshot`
3. 实验侧结果表已落地：
   - `quant_tradeability_signals`
4. Promotion 机制已落地第一版：
   - verdict
   - approval
   - promote
   - rollback
   - `promotion_audit_log`
5. Admin Tradeability 控制塔已存在：
   - 研究池/实验结果可看
   - 生产模式快照可看
   - promotion timeline 可看

### 3.2 还不是事实、只是目标的内容

1. “生产线和实验线的数据底座不同”：
   - 当前文档共识已改成这个说法
   - 但代码现状仍主要表现为“结果表分离”，不是“物理底座完全分离”
2. “promotion 已按三个核心模式并列治理”：
   - 当前并非如此
   - 现有 promotion 仍明显偏向默认模式 `balanced_v1`
3. “全仓库文档和页面术语已经统一”：
   - 当前也并非如此
   - 仍有旧文档/旧页面使用“产品池 / 研究线 / 生产流水线”等旧口径

---

## 4. 目标态（To-Be）

### 4.1 架构目标态

目标态应明确为：

1. 生产线和实验线在结果口径上完全分离
2. 生产线和实验线在数据底座上要么：
   - 物理分离
   - 要么逻辑分层并有明确边界
3. 不允许继续使用模糊表述，把“结果表分离”误说成“底座已经分离”

### 4.2 管理目标态

1. Admin 对生产线以“模式分别看绩效”为主
2. 不把模式总和作为核心管理指标
3. `仅观察` 单独标记，不与三类核心模式混作同类排名
4. promotion 逐步从“默认模式中心”升级为“核心模式治理中心”

### 4.3 文档目标态

1. 核心文档中文统一使用：
   - `生产线 / 实验线`
   - `生产池 / 研究池`
2. 英文概念统一保留：
   - `Production Decision Lane`
   - `Research Quant Lane`
3. 所有执行类文档必须区分：
   - 当前事实
   - 下一阶段目标
4. 不允许把未来态写成当前已实现。

---

## 5. 执行原则

### 5.1 先写实，再升级

文档修订必须遵守：

1. 当前实现是什么，就先写清楚是什么
2. 如果团队决定未来要改，再单独写“目标态 / 下一阶段”
3. 不允许把“正在讨论的原则”直接改写成“当前系统事实”

### 5.2 先收口核心文档，再清理外围文档

执行顺序应为：

1. 总词表
2. 核心运行手册
3. 产品 Spec
4. Admin Spec
5. Backend Runbook
6. Architecture / Feature Manifest / 产品更新文案
7. 前端后台页面文案

### 5.3 先统一口径，再改机制

当前顺序不建议反过来：

1. 先把语言和边界讲清楚
2. 再决定 promotion 是否升级为多模式治理
3. 再决定底座分离到底做到什么程度

原因：

如果连“当前事实”和“目标态”都没分开，后续代码和后台改动会持续反复。

## 6. 已拍板工程决策

以下 3 条为当前执行口径，后续工程实现默认以此为准，不再反复讨论。

### 6.1 底座策略

当前决定采用：

**共享底层数据，结果表与统计口径严格分离。**

具体含义：

1. 当前不追求生产线 / 实验线的物理底座分离。
2. 当前允许共用：
   - `daily_prices`
   - `ai_predictions_v2`
   - 同一数据库连接体系
3. 当前必须严格分离：
   - 生产线结果表
   - 实验线结果表
   - 后台展示口径
   - promotion 判断口径

这意味着：

1. 当前事实应表述为“共享底层数据 + 结果口径分离”。
2. 不再把“底座不同”当作当前已完成事实。
3. 若未来要升级到逻辑分层或物理分离，需单独立项。

### 6.2 Promotion 治理对象

当前决定采用：

**三个核心模式治理，默认模式重点展示，promotion 仍以 bundle 为执行单位。**

具体含义：

1. `稳健 / 平衡 / 进取` 纳入核心模式治理范围。
2. `平衡` 仍作为默认模式重点展示与重点观测对象。
3. promotion verdict 不应再只围绕 `balanced_v1` 单点判断。
4. 真正执行 promote / rollback 时，仍以：
   - `mode bundle`
   - `params bundle`
   为主要切换单位。

### 6.3 `仅观察` 的工程定位

当前决定采用：

**`仅观察` 是特殊类型的生产 mode。**

具体含义：

1. `仅观察` 属于正式生产模式。
2. 但它不参与：
   - 核心模式同类比较
   - 最优参数治理
   - promotion 核心门禁比较
3. Admin、API、文档都应显式标记它的特殊身份。

## 7. 分阶段执行方案

### Phase 0：文档收口（当前立即执行）

目标：

1. 把核心文档中的中文术语统一
2. 把 `仅观察` 的特殊模式定位写清楚
3. 把后台当前以“各模式各自绩效”为主的口径写清楚
4. 把“底座分离”明确标记为目标态，而不是已完成事实

本阶段输出：

1. 核心词表一致
2. 运行文档一致
3. 产品/后台 spec 一致

### Phase 1：事实核对（文档补真相）

目标：

1. 在 Engineering 文档中补一份明确的 As-Is 说明
2. 清楚写出当前代码实际依赖：
   - 哪些表共用
   - 哪些结果分离
   - promotion 现在看什么
3. 明确哪些是已实现、哪些是部分实现、哪些是未实现
4. 明确定义“数据底座分离”的实际含义，禁止继续停留在抽象口号

本阶段必须回答的 2 个问题：

1. 当前“底座分离”到底是：
   - 物理库分离
   - schema 分离
   - 还是仅结果表分离
2. 当前 promotion 是：
   - 只看 `balanced_v1`
   - 还是已经具备多模式扩展能力

### Phase 2：后台口径对齐

目标：

1. 把 Admin 页文案改成与最新词表一致
2. 把生产区说明改成：
   - 当前重点是各模式各自绩效
   - `仅观察` 为特殊模式
3. 避免页面继续使用旧词：
   - `产品池`
   - `研究流水线`
   - `生产流水线`

### Phase 3：机制升级决策

目标：

1. 决定 promotion 是否从“默认模式门禁”升级为“核心模式门禁”
2. 决定“底座分离”到底做到哪一级
   - 物理底座分离
   - 逻辑分层分离
   - 或维持共享底层数据、只做结果口径隔离
3. 把确定后的目标写回：
   - 架构文档
   - runbook
   - promotion 计划

注意：

Phase 3 才是机制升级阶段，不应在 Phase 0 和 Phase 1 里偷渡为既成事实。

## 8. 工程任务清单

### P0：数据结构与 verdict 收敛

1. 把 `metrics_tradeability_promotion.py` 从单 `balanced_v1` 产品效果门禁升级为三核心模式治理口径。
2. 增加 mode-level verdict summary 结构，至少覆盖：
   - `steady_v1`
   - `balanced_v1`
   - `aggressive_v1`
3. 将 `observe_only_v1` 明确排除在核心模式比较之外，但保留独立展示标记。

### P1：Admin API 收敛

1. 扩展 `/api/admin/tradeability`：
   - 返回默认模式重点视图
   - 返回三核心模式比较视图
   - 返回 `仅观察` 的特殊模式标记
2. 明确 API 字段层区分：
   - 正式生产绩效
   - 实验线结果
   - promotion 核心 verdict

### P2：Admin 页面收敛

1. 生产区改成“双层结构”：
   - 默认模式重点卡
   - 核心模式比较表
2. `仅观察` 在 UI 中单独标记，不与三核心模式混排为同类竞争
3. 页面说明统一强调：
   - 模式价值评估
   - 非收益承诺
   - 指标必须结合样本数和风险指标一起看

### P3：测试与回归

1. 更新 promotion 相关单测，覆盖三核心模式治理。
2. 更新 Admin API 聚合层测试。
3. 补充 `observe_only_v1` 的特殊分支测试。
